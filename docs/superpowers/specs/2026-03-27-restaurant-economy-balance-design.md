# 餐厅经济平衡重设计 - 客流分层与数据透明

> **状态**: 已完成 (2026-03-27)
> **创建日期**: 2026-03-27
> **设计者**: 头脑风暴 (Claude Code + 用户)

---

## 1. 问题陈述

当前餐厅系统存在三个核心问题：

1. **低级菜谱被完全淘汰** — 高级菜在利润率、绝对利润、品质倍率上全面碾压低级菜，无任何trade-off
2. **数据不透明** — 玩家看不到利润率、客流组成、产能利用率等关键经营数据，无法做策略决策
3. **缺乏策略深度** — 最优策略永远是"全上最贵的菜"，菜单配置没有意义

## 2. 设计目标

- 让不同等级菜谱都有存在价值，低级菜"薄利多销"，高级菜"高利润但客源有限"
- 让玩家能看到关键经营数据，做出有依据的策略决策
- 菜单搭配成为核心策略，混搭优于极端

## 3. 设计决策记录

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 低级菜优势机制 | 客流结构驱动 | 最自然，不需要硬编码速度加成，策略深度最好 |
| 客人分层数 | 3层 | 简洁清晰，策略选择明确 |
| 数据透明度 | 实用策略向 | 显示决策所需数据，信息密度高但不冗余 |
| 改动范围 | 全面改造 | 可新增命令、优化显示，大幅提升体验 |

## 4. 客流分层系统

### 4.1 客人类型定义

| 客人类型 | 标识 | 接受的菜谱等级 | 声望满意 | 声望不满 |
|---------|------|-------------|---------|---------|
| 普通食客 | COMMON | 白/绿 | +1/人 | -3/人 |
| 富商 | WEALTHY | 绿/蓝/紫 | +3/人 | -5/人 |
| 贵宾 | VIP | 紫/橙 | +8/人 | -2/人 |

说明：
- 普通食客不满惩罚较高(-3)：占比最大，大量不满会快速拉低声望
- 贵宾不满惩罚较低(-2)：贵宾"吃不到就走了"，不会大闹，但满意奖励很高(+8)
- 富商不满惩罚最高(-5)：富商期望高，失望后会给差评

### 4.2 声望对客流结构的影响

随声望增长，高消费客人比例逐步提升，但普通食客永远是最大群体：

```python
REPUTATION_CUSTOMER_RATIO = [
    (0,     {"common": 0.65, "wealthy": 0.28, "vip": 0.07}),
    (1000,  {"common": 0.60, "wealthy": 0.30, "vip": 0.10}),
    (3000,  {"common": 0.52, "wealthy": 0.35, "vip": 0.13}),
    (5000,  {"common": 0.45, "wealthy": 0.38, "vip": 0.17}),
    (8000,  {"common": 0.40, "wealthy": 0.40, "vip": 0.20}),
]
```

查表逻辑：取不超过当前声望的最大阈值对应的比例。

注意：即使声望为0，也有7%的VIP客人。这是有意设计——新餐厅也能偶尔接触高端客群，提供成长动力和"惊喜收入"。

### 4.3 客人与菜品的匹配映射

```python
CUSTOMER_TIER_RECIPE_MAP = {
    "common":  ["white", "green"],
    "wealthy": ["green", "blue", "purple"],
    "vip":     ["purple", "orange"]
}
```

注意绿色菜被普通食客和富商共同接受，是衔接两个群体的"万金油"等级。

### 4.4 结算流程改动

原流程：
```
所有客人 → 从所有菜品中随机消费
```

新流程：
```
1. 计算总客流（公式不变）
2. 按声望查表拆分为3组：common_count, wealthy_count, vip_count
3. 厨师做出的菜品按 recipe.tier 分类到3个桶
4. 每组客人按顺序消费匹配桶中的菜品
5. 未被消费的菜品 = 浪费（不产生收入，不影响声望）
6. 未被满足的客人 = 声望惩罚（按上表计算）
7. 日志记录各组的满足率
```

**共享tier菜品的分配优先级：** 当多个客群接受同一tier菜品时（如绿色被common和wealthy共同接受，紫色被wealthy和vip共同接受），按 **common → wealthy → vip** 的顺序分配（先满足低层客群）。理由：低层客群数量最多、不满惩罚累积最大，优先满足可最大化声望。

详细匹配逻辑：
```
# 将所有做出的菜品按tier分桶
dish_pool = {tier: [dishes...] for tier in all_tiers}

# 按优先级顺序分配（先common，再wealthy，最后vip）
for 客人类型 in [common, wealthy, vip]:
    可消费tiers = CUSTOMER_TIER_RECIPE_MAP[类型]
    可用菜品 = 从dish_pool中取所有属于可消费tiers的菜品（已被前面客群消费的不再可用）
    served = min(该组客人数, len(可用菜品))
    从可用菜品中取前served道计算收入，并从dish_pool中移除这些菜品
    unserved = 该组客人数 - served
    声望惩罚 += unserved × 对应惩罚值
    声望奖励 += served × 对应奖励值
```

这意味着：若菜单只有绿色菜，common会优先吃掉绿色菜，wealthy只能吃剩余的。这激励玩家为每个客群准备专属tier菜品，而非靠"万金油"tier。

## 6. 声望计算改动

### 6.1 新的声望变化公式

替换原有的统一声望计算（原来是每人随机+1~3/-2~5），改为按客人类型分别计算固定值。改为固定值的设计意图：让声望变化可预测，玩家能通过数据面板精确评估菜单调整的效果，而非靠运气。

```python
reputation_change = 0

# 按客人类型计算
for tier in ["common", "wealthy", "vip"]:
    served = tier_served[tier]       # 该类型被满足的客人数
    unserved = tier_unserved[tier]   # 该类型未被满足的客人数

    # 满意奖励
    reputation_change += served * SATISFACTION_BONUS[tier]

    # 不满惩罚
    reputation_change -= unserved * DISSATISFACTION_PENALTY[tier]

# 完美菜肴额外奖励（保留）
reputation_change += perfect_dish_count * 5

# 黑暗料理惩罚（保留）
reputation_change -= dark_dish_count * 2
```

### 6.2 声望奖惩配置

```python
SATISFACTION_BONUS = {
    "common": 1,
    "wealthy": 3,
    "vip": 8
}

DISSATISFACTION_PENALTY = {
    "common": 3,
    "wealthy": 5,
    "vip": 2
}
```

## 8. 策略模拟验证

### 场景：餐厅等级5，声望2000，30席，3个蓝色厨师（速度4道/时）

**场景1：纯白色菜单**
- 客流：~20人（普通12 / 富商6 / 贵宾2）
- 产能：12道白色菜
- 普通食客：12人全满足，收入 12×120 = 1,440金
- 富商：6人无菜可吃 → 不满 -30声望
- 贵宾：2人无菜可吃 → 不满 -4声望
- 声望：+12 -30 -4 = **-22**
- 结论：收入低(1,440金)且声望暴跌(-22)，不可持续

**场景2：纯紫色菜单**
- 产能：12道紫色菜
- 分配顺序：common先 → 普通食客不接受紫色，跳过
- wealthy：6人可吃紫色，消费6道，收入 6×4,200 = 25,200金
- vip：2人可吃紫色，消费2道，收入 2×4,200 = 8,400金
- 合计售出8道，**4道浪费**（无人消费，食材成本已扣）
- 普通食客：12人无菜可吃 → 不满 -36声望
- 声望：+6×3 +2×8 -12×3 = 18+16-36 = **-2**
- 结论：收入高(33,600金)但4道菜白做浪费食材，且声望缓慢下降(-2)，长期不健康

**场景3：混搭菜单（白4 + 绿4 + 蓝4）**
- common(12人)：可吃白4+绿4=8道 → 满足8人，4人不满（绿色全被common吃完）
- wealthy(6人)：绿已耗尽，仅剩蓝4道 → 满足4人，2人不满
- vip(2人)：无紫/橙菜 → 2人不满
- 收入：白4×120 + 绿4×500 + 蓝4×900 = 480+2,000+3,600 = **6,080金**
- 声望：+8×1 +4×3 -4×3 -2×5 -2×2 = 8+12-12-10-4 = **-6**

**场景4：优化混搭（白5 + 绿5 + 蓝2）**
- 普通食客12人 → 白5+绿5=10道（满足10人，2人不满）
- 富商6人 → 蓝2（满足2人，4人不满）
- 贵宾2人 → 无菜（2人不满）
- 收入：5×120 + 5×500 + 2×900 = 600+2500+1800 = **4,900金**
- 声望：+10×1 +2×3 -2×3 -4×5 -2×2 = 10+6-6-20-4 = **-14**

**场景5：最优混搭（白5 + 绿3 + 蓝2 + 紫2）**
- 需厨房Lv4解锁紫色，产能12道
- 分配顺序 common → wealthy → vip：
- common(12人)：可吃白+绿 = 5+3 = 8道 → 满足8人，4人不满
- wealthy(6人)：可吃绿+蓝+紫，但绿已被common吃完 → 蓝2+紫2 = 4道 → 满足4人，2人不满
- vip(2人)：可吃紫+橙，但紫已被wealthy吃完 → 0道 → 2人不满
- 收入：白5×120 + 绿3×500 + 蓝2×900 + 紫2×4,200 = 600+1,500+1,800+8,400 = **12,300金**
- 声望：+8×1 +4×3 -4×3 -2×5 -2×2 = 8+12-12-10-4 = **-6**

**场景6：跳过蓝色直上紫色（白6 + 绿4 + 紫2）**
- 产能12道，放弃蓝色直接上紫色
- common(12人)：白6+绿4 = 10道 → 满足10人，2人不满
- wealthy(6人)：绿被common吃完，紫2 → 满足2人，4人不满
- vip(2人)：紫被wealthy吃完 → 0人满足，2人不满
- 收入：6×120 + 4×500 + 2×4,200 = 720+2,000+8,400 = **11,120金**
- 声望：+10×1 +2×3 -2×3 -4×5 -2×2 = 10+6-6-20-4 = **-14**
- 对比场景5：收入略低(11,120 vs 12,300)，声望更差(-14 vs -6)，说明跳过蓝色不划算——蓝色菜给wealthy带来的稳定收入不可忽视

### 场景对比汇总

| 场景 | 菜单配置 | 收入 | 声望变化 | 评价 |
|------|---------|------|---------|------|
| 1 | 纯白 | 1,440 | -22 | 收入低+声望暴跌 |
| 2 | 纯紫 | 33,600 | -2 | 收入高但4道浪费+声望负 |
| 3 | 白4+绿4+蓝4 | 6,080 | -6 | 中等收入，声望微负 |
| 4 | 白5+绿5+蓝2 | 4,900 | -14 | 偏保守，声望很差 |
| 5 | 白5+绿3+蓝2+紫2 | 12,300 | -6 | 收入最高的混搭 |
| 6 | 白6+绿4+紫2 | 11,120 | -14 | 跳过蓝色不划算 |

**结论：** 产能(12道)无法同时满足所有20人客流。核心策略是在 **收入最大化** 和 **声望维护** 之间找平衡。场景5是收入最高的方案，但所有场景声望都为负——这说明3个厨师12道产能不够用，需要更多厨师。这创造了明确的成长动力：升级餐厅不只是解锁高级菜，更是扩大产能来同时服务各层客群。

## 11. 补充说明

### 11.1 未售出菜品处理

未被消费的菜品（做了但没有对应客群购买）不产生收入，但其食材成本已在烹饪步骤中扣除，不退还。这是"浪费"的代价，激励玩家合理配置菜单。

### 11.2 随机经营事件与客流分层的交互

现有代码中 `extra_customers` 事件（如"节日旺季"+5人、"大雨天气"-4人）直接修改总客流。在新分层机制下，额外/减少的客人**按当前声望对应的比例分配到三个层级**。分配规则：按比例乘以额外人数，各层向下取整，**取整后的剩余人数全部归入common层**（因为common是最大群体，小数归入不影响平衡）。例如声望2000时，+5人 → common+3, wealthy+1(1.5向下取整), vip+0(0.5向下取整)，剩余1人归入common，最终common+4, wealthy+1, vip+0。

### 11.3 菜品在共享tier中的消费顺序

当一个客群有多个可消费tier时（如wealthy可消费绿/蓝/紫），优先消费**最高tier**的菜品。理由：富商/贵宾倾向于点贵的菜，这也让高级菜在有限客源下优先被消费。
