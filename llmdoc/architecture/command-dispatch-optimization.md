# NoneBot 指令分发优化：减少无关规则检查与异步任务

## 问题与实际反馈

项目使用 NoneBot 2.5.0，包含 552 个普通指令处理器，以及日志、正则匹配、装备选择、剧情等监听器。用户反馈机器人曾有明显卡顿；第一轮指令名提前筛选上线后，反馈为“一下子就不卡了”。这是实际使用体验，尚不是生产环境延迟分位数或吞吐量测量。

原生机制已经使用 Trie 前缀树识别指令名，但识别以后仍按 priority 从小到大枚举响应器，同层并发检查事件类型、权限和规则。指令规则通过通用依赖调用执行；名字不匹配的普通指令也会付出外层任务、规则子任务和运行时依赖参数解析的成本。

552 个指令处理器中，551 个已设置 `block=True`。block 只能在命中并处理后阻止后续优先级层，不能省掉前面层和同层已经创建的检查任务；普通聊天没有命中指令，也不会触发这些指令的阻断。因此问题不是缺少 block。

## 第一轮：把指令名检查提前

实现位置：`plugins/xiuxian_game/command_dispatch.py` 中的 `CommandDispatchRule`。

在普通指令规则入口读取 NoneBot 已解析的 `state[PREFIX_KEY][CMD_KEY]`，检查是否属于原生 `CommandRule.cmds`。该集合包含指令名和别名。

```python
if command not in checker.cmds:
    return False
return await super().__call__(bot, event, state, stack, dependency_cache)
```

仅处理本游戏纯单一原生指令规则；复合规则和自定义规则保持原流程。名字匹配后仍由 NoneBot 处理参数、空白限制等验证。

这轮仍按优先级枚举响应器，也保留外层响应器任务及权限检查。收益来自避免对无关指令调用完整规则依赖链，不能表述为直接路由或 O(1) 查找。

## 第二轮：在创建响应器任务前筛选候选

同一文件中的 `CommandMatcherProvider` 通过公开的 MatcherProvider API 接入响应器注册表。在每层枚举时，使用 Python 字典构造指令名到候选响应器位置的映射，合并仍需通用检查的监听器，保持注册顺序，然后让原生调度创建候选任务。

概念上相当于 Java 的：

```java
Map<Command, List<Handler>> commandIndex;
```

值为列表，是因为同名指令可以有多个处理器。例如副本和跑商都使用“购买”：副本 priority=5，检查后可以放行；跑商 priority=7。不能覆盖其中一个，也不能在查表时提前替业务决定阻断。

```text
QQ 事件 → 原生预处理 → Trie 解析指令名
    → 当前 priority 的指令候选 + 通用监听候选
    → 原生权限、规则、业务处理
    → 原生 block 判断 → 下一层
```

通过事件上下文绑定当前 state 和调度父任务，使候选过滤只作用于框架调度枚举。业务函数、同步工作线程和其他注册表读取仍可看到完整列表；append/remove 等操作写入真实注册表。事件上下文借助原生 AsyncExitStack 清理。

这版每层仍同步扫描注册结构并构造 Map，以及时反映注册、删除及规则原地修改。其收益是减少外层异步检查任务，**整体分发仍存在 O(N) 扫描，不能称为持久 O(1) 路由**。

### 兼容边界

- 保留优先级、同层并发、同名指令以及 block 行为。
- 命中候选仍执行原生参数与权限检查。
- 临时会话、可过期处理器、自定义规则等保留原生处理机会。
- 原生 Trie 解析失败时使用全量候选，避免把解析异常误当成普通聊天。
- 自定义规则在同层检查时改写共享指令名，会破坏提前候选选择的前提。已加入保守整层回退：遇到未知规则、权限、额外依赖或覆盖的检查方法，该层使用全量枚举。空 Rule、已知原生规则和权限在验证依赖结构后允许继续筛选。已加入同层指令重写、上下层变化及回退范围回归测试。
- Provider 接口是公开的，但事件上下文绑定使用 `_apply_event_preprocessors` 薄包装，另包装 Trie 成功解析标记。依赖 NoneBot 2.5.0 的调用顺序；框架升级时必须复核真实事件分发测试。

## 已获得的性能证据

只读复核使用真实 `Matcher.new` 和 `handle_event` 创建 550 条无关普通指令及 1 个命中处理器。551 条均满足索引条件，无通用 fallback；关闭日志，每个场景预热 5 次、测量 60 次。下表为本机平均分发耗时，单位毫秒。

| 方案 | 指令消息平均 | 普通聊天平均 | 每事件外层任务数：指令 / 聊天 |
| --- | ---: | ---: | ---: |
| NoneBot 原生规则 | 634.405 | 655.684 | 551 / 551 |
| 第一轮提前筛选 | 32.503 | 26.589 | 551 / 551 |
| 第二轮候选索引，兼容保护补充前 | 9.772 | 6.386 | 1 / 0 |

该场景中，第一轮的指令分发耗时约为原生的 1/19.5；第二轮约为第一轮的 1/3.3。数字只代表这一组本机模拟。实际项目包含权限规则和监听器，不能把该倍数直接当成生产加速倍数；后续安全回退也会影响可索引范围。

另一个自动化场景注册 42 个响应器，命令消息只调度 2 个候选，普通聊天只调度 1 个监听候选。测试直接记录 `check_and_run_matcher` 调用集合，比单纯用时间阈值更能稳定证明无关任务已被省掉。

性能限制：没有测量生产端到端 p50/p95/p99、吞吐量、CPU 或 Redis 延迟。QQ 接收/回复网络、数据库和业务执行仍影响玩家看到回复的时间。

### 最终版本实际注册表覆盖

补充保护后检查了项目实际注册的 15 个优先级层，均没有触发未知规则导致的整层回退。选取三个主要层的候选枚举结果如下：

| Priority | 注册响应器数 | 可索引数 | 普通聊天候选数 | “购买”候选数 |
| --- | ---: | ---: | ---: | ---: |
| 5 | 147 | 143 | 4 | 5 |
| 7 | 66 | 61 | 5 | 6 |
| 13 | 81 | 80 | 1 | 1 |

这证明安全保护没有让实际游戏的常用层失去索引优化。这些数字是注册表枚举结果，不是端到端时延；实际是否运行后续层仍由原生 block 决定。“购买”在 priority 5、7 分别保留对应处理器。

## 面试说明示例

> 我的 QQ 游戏机器人有五百多个指令。排查卡顿时发现，框架虽然用前缀树解析出了指令名，之后仍对大量不相关处理器创建异步检查任务、解析规则依赖。我先把指令名判断放到完整规则调用之前，实际使用中的卡顿明显改善。随后通过框架的 Provider 接口加入指令候选索引，在创建任务前排除无关普通指令，并保留同名指令、优先级阻断和会话监听。在本机 551 个普通指令的模拟里，外层任务从 551 个降到 1 个，平均分发耗时从提前过滤版的约 32.5 毫秒降到约 9.8 毫秒。这是模拟结果，我通过调度任务计数和行为回归验证机制，没有把它说成生产接口延迟。

可展开讨论的技术点：通用框架与专用路由的取舍、异步任务开销、提前过滤、索引失效与动态规则、ContextVar 的任务继承、功能等价测试、微基准与生产体验的区别。
